# 静态自检与问题排查

## 1. 自检与交付

源码核对、Lua 静态解析和资源结构检查都不能代替游戏运行。交付时简述已做的检查及尚未验证的游戏行为，提供针对本次功能的验收步骤（见 `workflow.md` §5）。游戏测试由用户完成；涉及联机时建议远端客机另行确认。

## 2. 静态自检脚本：`scripts/check_mod.py`

纯标准库、只读、无需装 luaparser／lupa。做的事：

- **Lua 5.1 静态解析**：自动寻找 `luac5.1`、`luac-5.1`、`luac` 或兼容 Lua 5.1 解释器，并检查版本；使用 `luac -p` 或只 `loadfile` 编译，不运行模组。其它版本（例如 Lua 5.4）不能冒充 5.1。无匹配解析器或指定 `--no-luac` 时只做词法/块配对扫描，识别普通/长字符串与注释；无法证明 Lua 语法正确。即使 5.1 解析通过，Klei 自定义的引擎运行时仍须另验。
- **资源路径核对**：检测常见 `Asset(...)` 字面量路径是否精确存在于模组目录，不把其他目录中的同名文件算作匹配；动态或转义路径标未查，模组目录不存在的路径标未解析（可能来自官方或其他资源）。只验证存在性，不证明资源内容和引擎解析契约。
- **XML 图集纹理**：检查模组目录内 Atlas XML 中的 Texture filename 相对于 XML 的文件是否存在（Element 名称不当作文件名）。`ATLAS_TEXTURE_UNRESOLVED` 为本地纹理缺失，`ATLAS_TEXTURE_UNCHECKED` 为缺少声明、非相对或无法在模组内核实的路径，`XML_UNCHECKED` 为 XML 读取或解析失败；分别统计，不改变 Lua 语法退出码。通过不证明纹理格式、UV、引擎解析或实际 UI 显示正确。

用法：

```bash
python scripts/check_mod.py <模组目录> [--no-luac | --luac <Lua5.1工具>] [--new-mod] [--json]
```

退出码：**0** = 所有 Lua 文件被兼容 5.1 解析器实际解析且无解析错误；**1** = 解析错误或词法疑点（查看 kind 区分）；**2** = 参数/输入错误；**3** = 未全部完成真实解析（只有词法扫描、读取失败或解析器异常）。JSON 的 `file_checks.method` 逐文件记录 `lua51_parse`、`heuristic_only` 或 `unreadable`；资源未解析/未查单独计数，不改变语法退出码。0 也不是整体 PASS。

新建或整体重构任务使用 `--new-mod`，额外报告 `new_mod` 提示：入口直接导入 postinit、装配层直接调用常见 hook API、手工 RegisterSinglePrefab、公共表不在 init、init 与 prefab 字面量资产声明重复、`AddRecipe2` 无显式分类、字面量 `Ingredient` 不在注解及本地字面量 Prefab 声明。普通局部修改按实际结构选择。提示不改变语法退出码，也无法判断任意共享表包装、执行端、动态注册及函数调用契约；注解可能滞后、特殊写法可能有意如此，核对当前源码及依赖后处理。

按任务需要运行，并如实报告方法、未解析文件、资源未查项及引擎内未测风险，不因用户熟练程度区别验证质量。

`--new-mod` 还按原版 `mods.lua` 的规则检查字面量 `modimport` 路径，从模组根目录查找，缺少 `.lua` 后缀时自动补上。`MODIMPORT_MISSING` 给出缺失文件和调用行；动态表达式、含转义或无法在模组内核实的路径记为 `MODIMPORT_UNCHECKED`。两者均为提示，沿用上面的语法退出码。

## 3. 崩溃与性能排查

**崩溃排查**：先取**第一条**相关错误、完整堆栈和前置警告，后面的连锁 nil 通常不是根因；沿堆栈进模组代码，用当前源码查原版调用契约，别只在报错行加 nil 判断，也别用 `pcall` 包整段逻辑或无条件 nil return 掩盖状态损坏。展开顺序：入口 → Hook → Prefab → Component/Replica → Action/SG → RPC/UI → 保存路径；先查崩溃、存档损坏、非法客户端写入，再查初始同步、任务/事件清理、退出与旧档路径，最后看资源、本地化、性能。堆栈里 `workshop-<id>` 的 `<id>` 是创意工坊模组号，映射到 `<workshop-root>/<id>`，不是 `mods/workshop-<id>`。

日志位置与回传要求见 `workflow.md` §5。

**性能剖析**：先根据可重复场景、日志或实际数据定位热点，再按服务端、网络、客户端检查高频实体查找、更新任务、UI 刷新和对象清理。按实测结果减少不必要的更新、搜索或分配；保持权威逻辑正确。

## 4. 发布前检查与版本升级复核（流程的尾巴）

**发布前**：按本次改动过一遍 modinfo／配置、资源注册路径、生命周期与存档、资源引用、界面／联网、本地化。角色清单从当前源码取；modicon 与库存图标按实际消费者和资源契约检查；保留 `mod.manifest` 与 Workshop 内容。测试通过不自动等于可发布——作者决定项、未测项、证据路径单列。

**版本升级后**：读当前 version.txt，按相关符号重新检查实际 API、调用时机、端别和资源变化；只针对受影响的机制修订与给出验收要点，交付说明本次基准版本。
