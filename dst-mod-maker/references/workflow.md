# 工作流细则：澄清、判定、自检

## 1. 需求澄清

先问清楚，再规划，再做。提问只覆盖会改变实现的关键项，不做问卷式盘问。

**不预设功能影响的对象类别**——可能是玩家、生物、世界物件或其它，按描述本身判断。

**不预设功能数量**——使用者描述的是整个模组内容，通常同时包含多个功能点。先把描述分析拆解成功能清单，弄清每个功能点要做什么、彼此有无依赖、共用数据或冲突，再进入规划；不要把「一个模组」当成「一个功能」来做，也不要只挑一个最显眼的做。功能点多不等于要多问，拆解本来就是技能侧的活。

通常会先确认会改变实现的点（有现成信息就不必问）：

- 是否要新物品或新外观。
- 目标游戏版本（优先读 `<game_root>/version.txt`，数字不一致时再确认）。

默认（不主动问，采纳后自行记录；使用者要求时再列出）：

- 配置项不加。
- 不做额外兼容层；能 hook 尽量 hook。
- 美术优先复用官方资源。
- 需求未提到多人差异时按「联机下也要正常」实现。

## 1.1 自适应交流

看实际表达、已有上下文和明确偏好；术语、素材路径、日志只是信号，不是能力测试。效果描述为主时用大白话与默认实现；技术讨论或主动要求 review 时给功能拆解、接口、两端职责、依据和关键取舍。无需询问能力等级，可随对话调整；自检、证据和资源工具对所有用户同样可用。显式指定优先于默认，发现与事实/需求冲突时说明。

按 `SKILL.md` 的任务路线读取对应参考。新建默认到游戏 mods 目录；局部修改/优化定位实际副本与入口、配置、附近代码，保留无关结构；整体优化/重构采用约定结构，无需再次点名 skill。审查及 API 解释不自动改文件；调试先定位日志和复现路径再按请求修复。
## 2. 端型判定（默认服务器/所有端模组）

**默认写 `all_clients_require_mod = true`**，不必逐项询问端型。明确需要另外两类时核对可行性。

| 字段 | 含义 | 何时用 |
|---|---|---|
| `all_clients_require_mod = true` | 服务端 / 所有端模组（俗称服务器模组） | **默认**，绝大多数情况直接写它 |
| `client_only_mod = true`，`all_clients_require_mod = false` | 仅客户端模组 | 全部功能点都能在客户端实现，仍可使用原版允许的操作通道 |
| 两者均为 `false` | 服务端运行、不强制客户端安装 | 功能不要求客户端拥有本 mod 的代码、prefab、资源、动作或自定义网络协议 |

验证可行性时按每个功能点区分读 replica 与修改权威状态、原版允许的操作与必须有模组服务端的能力，以及客户端是否依赖新增代码/资源/动作/网络协议。不能仅因使用游戏已有的 RPC 就认定纯客户端不可行，也不能凭 `false` 字段保证无模组客机可用；验证无模组远端客机是否能正常加载并交互。

依据：`mods.lua` 中 `all_clients_require_mod` 读取点、`GetEnabledServerModsConfigData`，以及 `modindex.lua` 的 `GetServerModNames` / `GetClientModNames`。两字段互斥；不使用未找到加载器读取依据的 `server_only_mod`。写入前按当前源码复核。

判定后通常要理清：哪些逻辑只在服务端、哪些需要 replica、哪些需要 netvar / RPC；多个功能点能否共用同一套网络通道。这只是内部判断，不必向使用者汇报。

## 3. 规划（按需求展示）

规划供自身执行；按用户需要展示关键功能、取舍和依据。内容：

- 描述拆成哪几个功能点，各功能点分别对应哪些实体 / 组件 / 动作。
- 功能点之间的共享状态、依赖、实现顺序；多个功能共用同一 hook / 组件 / netvar / RPC 时是否合并、会不会互相覆盖。
- 用到的 hook 清单，以及为什么用 hook 而不是覆盖。
- 两端分工：服务端 SG 与客户端 SG 各需要什么。
- 网络：需要的 netvar 类型、RPC 方向。
- 资源：是否复用官方动画/贴图，是否需要使用者提供素材。
- 默认假设清单。

## 3.1 多系统优化／重构：分阶段，不丢功能

**按复杂度分阶段，而不是按行数划定大型模组。** 多子系统、共享配置/状态、跨端、旧档与资源依赖互相耦合时，即使代码不长也按此节；单一局部改动不需要这套流程。

1. **建立原有行为清单**：先读 `code_style.md`、`mod_structure.md`，再检查实际 `modmain`/导入链、modinfo、各功能块、配置键、公共 API 和资源。按功能记原行为、可调值、触发条件、hook、依赖、状态归属及可能影响旧档/联机的契约。用户明确要求的重命名或玩法调整单列；未要求的保留，不凭注释猜实现。
2. **按依赖划分阶段**：先整理入口、公共声明、配置和语言，再根据实际依赖处理组件、prefab、动作、状态图、UI 等系统。整体优化还需识别重复声明、手工 prefab 注册及重注册补救层、过度防御、竞争性 AI 循环等真实结构问题，核实可替代的官方机制后迁移，不能只搬文件。阶段顺序以项目真实依赖为准，不固定文件数。
3. **进入每阶段先读取导航**：按 `SKILL.md` 的子系统路线定位并阅读相关章节，再查当前官方实现与调用点；尤其核对改动的 API、回调参数、多返回值、执行端、初始化/销毁时机。新系统、用户纠正、长会话丢失上下文时重新读取对应约定；已读且当前可用的内容不用反复打开，也不用重新询问用户。
4. **每个阶段完成后复查实际改动**：检查该阶段导入与注册、原功能、回调契约、资源和用户明确要求的结构风格；根据影响范围用 §4 的相关项核对。不为满足代码风格删掉有实际作用的检查、事件或生命周期逻辑。发现新问题先修本阶段再继续；没有运行游戏不代表通过。记录简短的已完成阶段、相关证据/未核实风险，方便后续恢复工作，不必生成额外报告文件。
5. **最后按原行为清单整体比对**：每个原功能有对应实现、依赖/注册顺序正确、公共接口和配置/旧档兼容（用户明确授权的变更除外）、没有未经要求的行为变化；结构优化用 `check_mod.py --new-mod` 辅助检查，然后给本次受影响功能的进游戏验收要点。游戏测试仍由用户完成。

## 4. 自检清单（按相关性挑着核）

交付前必须以最终代码实际核对与本次改动有关的项；无关项直接跳过，不必逐项向用户汇报，也不规定打卡顺序。按功能路线逐项回查已实现或修改的功能；打开对应资料及当前官方关键调用方，比较成品调用、执行环境、状态与资源消费契约。发现偏离先判断是否有实际依据，否则修正并复核受影响调用；同一阶段已查清且仍在上下文的证据可以复用。自检不能只读清单而不看实际代码或当前源码。

1. **入口与两端**：按实际执行环境和阶段区分三个入口；共享声明两端一致，权威逻辑仅服务端。检查普通网络 prefab 的 PostInit 权威段是否明确使用 `TheWorld.ismastersim`，已知世界存在时不探测 nil，已知服务端组件或图名匹配的 hook 不机械加守卫（`code_style.md` §3）。
2. **动作与状态图**：按 `actions.md` 和 `stategraphs.md` 核对真实点击路径、候选显示、服务端最终结算、确定注册顺序、非 instant 的 ActionHandler 及需要的预测态；自建状态确认默认状态、实际生效帧、正常结束与中断清理。
3. **netvar**：两端声明是否完全一致、是否放在 `SetPristine()` 之前、是否落在 mastersim 分支之前；PostInit 里新增的 netvar 是否手动跑过一次 dirty handler 或由服务端重新 `set`。
4. **netvar 选型**：是否按位数/场景选了合适的类型；数组类是否可避免。
5. **RPC**：区分 C→S、S→C 和 shard→shard；注册名称/顺序一致；接收端按权威状态核验参数、身份、归属、是否仍可执行，跨分片考虑迟到、重复、迁移。
6. **事件**：`PushEvent` 只在同一环境内接收；需要双端同步时是否改用 netvar（netvar 变化会在双端触发 dirty 事件）。
7. **符号与资源**：`OverrideSymbol` / `Hide` 用的符号名、build 名是否存在；新增物品 prefab 的物品栏图标是否实际注册或显式指定已注册的原版图名，共用图集的图名/哈希及 XML 元素是否一致；本地图集 Texture filename 是否指向真实纹理，角色构造、皮肤及 UI 是否各自取到所需资源；`ATLAS_BUILD` 是否按画版用途声明（`anim_symbols.md` §5、`characters.md`）。
8. **可见性**：`RemoveFromScene` 不对玩家乱用；跟随特效是否处理了专用服务器不生成、客户端补建、OnRemoveEntity 清理。
9. **拼写与配方**：所有 prefab（含产物、`Ingredient` 的材料）、component / tag / action / 动画名按当前官方源码、实际资源和依赖核对，注解用于快速定位。普通新增配方显式选择实际用途的第五参数分类（`recipes_filter.lua`）；复用配方图标须核实真实图名。
10. **性能与行为**：服务端、网络、客户端三层分别检查；生物行为的 Brain/SG/locomotor 分工、目标有效性、路径、状态中断及清理；周期任务是否确有必要并处理休眠。
11. **默认项**：没有擅自加配置项、没有擅自加兼容层、没有生成美术文件。
12. **依据**：机制结论指向本次查询的实际文件、符号和必要时的行号，或说明验证依据与未核实范围。
13. **完整性**：逐项对照原始请求与成品，包括指定装备槽、精确触发方式、允许/拒绝目标与材料、独立数据和生命周期；不把头部装备变成手持装备等擅自更改明确需求。确认双语 `modinfo` 与独立语言文件的文本键和语言覆盖一致，先加载文字再使用本地化值注册动作。优化已有模组时核对改动前后的回调参数、返回值与生命周期契约。端型按请求与可行性确认。
14. **测试要点**：交付里是否覆盖了**每个**功能点的触发与预期，以及功能点之间的联动处，能照着做。
15. **结构与风格**：新建/整体重构逐个看生成文件：modmain 只导入 main，init 集中 PrefabFiles/公共 Assets，自有 prefab 由 scripts/prefabs 正常加载，hook 和原版共享表扩展由 main 转发到 postinit，不重复声明原版已注册或 prefab 局部 assets。优先现成事件/官方扩展 API；包装、提取或移动函数后逐一对照定义与实际调用点的参数（包括新增参数）、多返回值和作用域。运行 `check_mod.py --new-mod` 查看提示。
16. **功能专题（涉及才查）**：例如技能树查定义、图标/文字、两端 ID、激活/取消/重载与效果；轮盘从 execute 追到服务端结算，核对主机与客机分支、选中 ID、动作/选点、冷却与权限；范围击飞查实际目标 SG 对事件的处理及状态中断；旧档地图改造查选址、持久标记及地图数据写回。其它功能同样按对应专题与最终调用链核对。

## 5. 交付边界

交付能用的文件、必要说明、自检结果以及本次功能的验收提示；游戏测试由用户完成，遇到错误根据真实日志继续排查。

测试要点按这次实际做了哪些功能点来给，用大白话写、让使用者能照着做，通常包含：

- 启用模组进世界，先确认能正常加载、模组列表没有报错。
- **每个功能点**的触发步骤与预期表现，一句话能验完最好；功能之间有联动时补一条联动验证。
- 涉及联机、客户端预测或动画同步时，建议主机和远端客机分别确认；仅按本次功能需要考虑专服、洞穴或延迟补偿开关。
- 涉及存档、持续效果和实体生命周期的功能，按实际影响提示用户确认保存重载、重连、取消或移除等路径。
- 崩了看日志（Windows 在 `~/Documents/Klei/DoNotStarveTogether/`）：森林 `master_server_log.txt`、洞穴 `caves_server_log.txt`、客户端 `client_log.txt`，顶层为最近一次运行的对应日志；洞穴及客户端日志按实际运行环境存在。历史服务器日志去 `<用户id>/Cluster_<n>/Master|Caves/server_log.txt`，客户端历史日志去 `backup/client_log/client_log_<日期时间>.txt`。回传**第一条**相关 `LUA ERROR stack traceback:` 及完整堆栈。
- 如实说明已核对的源码、静态检查及尚未验证的游戏行为，别把未运行的功能说成已通过。

只列与本次功能点相关的项，不做通用问卷、不甩术语。静态自检、崩溃排查与性能定位见 `verification.md` §1～3。

## 6. 交付之后：发布前检查与版本升级复核

这不是每次都跑的门禁，是涉及发布或游戏更新时才做的尾巴，细节见 `verification.md` §4。

- **发布前**：按本次改动过一遍 modinfo／配置、资源注册路径、生命周期与存档、资源引用、界面／联网、本地化。测试通过不等于可发布——作者决定项、未测项、证据路径单列，不替使用者发布。
- **游戏更新后**：按 `verification.md` §4，以当前源码和资源重查本次受影响的机制。
